# 과적합 vs 일반화 실험 사전 등록

> 작성 2026-10-03, **측정 전 커밋**. 목적: 이 평가 체계가 "GT에 맞춘 점수 상승"과 "실제 성능 상승"을 구별하는지 검증

## 1. 설계

| 항목 | 내용 |
|---|---|
| GT | `eval/gold/gold_v2.jsonl` v2.2, 100문항 |
| 분할 | dev 44 · test 56 (`eval/gold/splits.json`, v2 확정 시 고정) — 두 방법 모두 **dev만** 보고 제작·조정 |
| 기준선 | 최종 구성(조 전체 색인 · 판례 연결 · top-5 · τ 0.50 · gen-v3-precedent) = `eval/results/v2/v2-final` |
| 노이즈 바닥 | 기준선 동일 설정 3회(기존 1회 + `--no-cache` 2회) → 전체·dev·test·유형별 범위 |
| 판정 | 1·2차와 동일: \|Δ\| > 노이즈 범위 **그리고** 문항 대응 부트스트랩 95% CI가 0 제외 |
| 주 지표 | M4_complete (dev·test 각각) |
| 핵심 판정량 | **일반화 격차 = Δdev − Δtest** |

## 2. 방법

### ① 과적합: dev 문항을 예시 저장소로 재사용 (`--fewshot-dev`)
- 질의와 가장 가까운 dev 문항 3개(KURE-v1 코사인)의 질문·참고 답안을 프롬프트에 "참고 예시"로 추가
- dev 문항은 자기 자신이 1위 예시 → 정답 열람(평가셋 누수)
- test 문항은 비슷한 dev 예시만 열람 → 정상적인 few-shot 효과만 존재

### ② 일반화: 하이브리드 검색 (`--hybrid`)
- 조 전체 색인의 의미 검색 + 문자 2-gram BM25 키워드 검색 → Reciprocal Rank Fusion
- GT 내용 미사용, 가중치·후보 수는 dev 검색 지표(Recall all·MRR, LLM 호출 없음)만으로 결정
- 근거: 2차 실패 원인 1위가 검색(Recall all 0.696), 법률 용어는 표면 일치가 강함

## 3. 예측

| 방법 | dev 완전 정답 | test 완전 정답 | 일반화 격차 |
|---|---|---|---|
| ① 과적합 | **유의 상승** | 노이즈 내 | 큼 (dev만 상승) |
| ② 하이브리드 | 상승 | 상승 (dev와 비슷한 폭) | 작음 |

- ② 보조 예측: dev·test 모두 Recall(all) 상승, 상승 폭 차이 작음
- ① 부작용 예측: 입력 토큰 증가, test에서 예시 답안 문체·내용이 섞여 근거 없는 주장 증가 가능
- 예측이 틀리는 경우도 그대로 보고
  - ①의 test가 유의 상승하면 "정상 few-shot 효과"로 해석
  - ②의 test가 정체하면 "dev 조정이 dev에 과적합"으로 해석

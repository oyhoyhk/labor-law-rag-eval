## 0. 결정 요약

- 품질 정의 = **정답성 · 근거 충실성 · 응답 거절 정확도** 3축 + 운영 지표(비용·지연)
- 측정 = 결정적 지표(검색·거절·인용) 우선, LLM Judge는 체크리스트 이진 판정에 한정
- 개선 증명 = 노이즈 바닥(동일 조건 3회) 측정 후, 그 폭을 넘는 차이만 유의로 판정
- Corpus = 노동법령 묶음(공공 저작물, 저작권법 7조) — **확정**
- **시행 상태 연결 주입** = 검색된 조문에 부칙의 시행일·유효기간·적용례·경과조치와 위임 시행령을 결정적으로 연결해 함께 주입
- Gold Set = **L1 단순 사실 → L5 판례 사례형** 난이도 단계, 판례형 정답은 판결요지(전문가 작성 근거)로 판정
- LLM = **엘리스 ML API의 GPT-5.6 Luna 단일 사용**(답변 생성 + Judge)
- Embedding = **로컬 nlpai-lab/KURE-v1**(bge-m3 한국어 검색 파인튜닝 · ML API 카탈로그에 임베딩 모델 부재, 크레딧 0원)
- 예산 = 크레딧 5만원 중 약 2만원(40%) 사용 계획, 실행당 하드 상한 설정

## 2. Part A — RAG QA 서비스 (MVP)

### 2.1 아키텍처

```
[fetch] law.go.kr XML ──► data/raw/*.xml (스냅샷)
   │
[ingest] parse ─► 조/항/호 구조 JSONL ─► chunk ─► KURE-v1 임베딩 ─► FAISS(IndexFlatIP) + chunks.jsonl
   └─► 부칙 파싱 · 개정 태그 · 위임 참조 ─► provision_graph.json (조문별 시행 상태 · 연결 조문)
   │
[serve] FastAPI
   POST /v1/query ─► retrieve(top-k) ─► 연결 확장(부칙·위임) ─► 거절 게이트(τ)
                 ─► Luna 생성(JSON) ─► 인용 검증 ─► 응답 / SSE
   │
[trace] 요청별 JSONL: 질의 · 검색 id/점수 · 프롬프트 해시 · 토큰 · 비용 · 지연
```

### 2.2 기술 스택과 근거

| 구성 | 선택 | 근거 |
|---|---|---|
| 언어/런타임 | Python 3.12 + uv | 임베딩·평가 생태계, lockfile 재현성 |
| API | FastAPI + Pydantic v2 | 스키마 정의 = 문서화(OpenAPI) 자동화 |
| Embedding | **nlpai-lab/KURE-v1** (dense 1024d, 로컬 MPS) · revision `8b418a58414668e75532ed045c22d9ca018ae2b2` 고정 | bge-m3 기반 한국어 검색 파인튜닝, MIT, 8,192 토큰 입력으로 긴 조문 절단 없음, 크레딧 0원 |
| Vector index | FAISS IndexFlatIP | 청크 수천 개 규모 → 정확 검색, 결정적 결과, 외부 서비스 불필요 |
| 키워드 검색(실험용) | BM25 + kiwipiepy 형태소 분석 | 조문 번호·법률 용어 정확 일치 보강 |
| LLM | GPT-5.6 Luna (ML API, OpenAI 호환) | 입력 304원·출력 1,827원/1M 토큰, 단일 모델 운영 |
| 프레임워크 | LangChain/LlamaIndex 미사용 | 파이프라인 전 단계 직접 구현 → 면접 설명 가능성 확보 |

### 2.3 Chunking 전략

- 기준선(baseline): **고정 길이 512토큰, 오버랩 64** — 통상 기본값
- 개선안(Part C H1): **조문 구조 단위**
  - 1 청크 = 1 조(article), 길면 항 경계에서 분할
  - 청크 앞에 `[법령명 > 장 > 제N조(조제목)]` 헤더 부착 → 검색 문맥 보강
  - 메타데이터: law_id, 조번호, 항번호, 시행일, 원문 URL
- 근거: 법령 인용의 자연 단위 = 조, 고정 길이 분할은 조문 중간 절단 + 출처 경계 붕괴 유발

### 2.4 시행 상태 연결 주입 (Provision Graph)

- 문제: 최신 공포본 본문에 **미시행 개정**과 **효력 상실 조항**이 섞여 있어, 본문만 주입하면 틀린 답을 정확하게 인용하는 상황 발생
  - 예: 제60조⑤ 연차 시간단위 분할(2027-06-10 시행), 제54조① 단서(2026-12-10 시행), 제53조③(2022-12-31 효력 상실)
- 원칙: **시행 상태는 인제스트 단계에서 결정적으로 산출**, LLM은 결과를 서술만 함 — 날짜 산술을 LLM에 맡기지 않음
- 1차 소스 = **공식 시행예정 버전**: 현행과 시행예정 버전의 조·항 텍스트 diff → 변경 조문에 공식 시행일 부여 (부칙 정규식 파싱보다 신뢰도 높음)
- 2차 소스 = **부칙 파싱**: 유효기간(효력 상실)·적용례·경과조치처럼 버전 diff로 드러나지 않는 조건만 담당
- 그래프 구성 (`provision_graph.json`, 노드 = 조·항)

| 엣지 | 추출 방법 | 예 |
|---|---|---|
| 개정 이력 | 항 끝 `<개정 YYYY.M.D>` · `<신설 …>` 태그 | 제60조⑤ ← 신설 2026.6.9 |
| 시행일 | 부칙 제1조 본문 + 단서의 "제N조(제M항)의 개정규정은 …부터 시행" | 제54조 ← 공포 후 6개월 경과 |
| 유효기간 | 부칙 "…까지 효력을 가진다" | 제53조③ ← 2022-12-31까지 |
| 적용례 · 경과조치 | 부칙 "적용례" · "경과조치" 조문 → 대상 조문 번호 | 제60조 ← 시행 전 발생 연차는 종전 규정 |
| 위임 | 시행령 "법 제N조제M항에 따른" 역참조 | 근기법 제11조③ → 시행령 제7조의2 |
| 내부 참조 | "제N조제M항에 따른" | 제56조① → 제53조 |

- 날짜 계산 규칙(부칙 파싱 시): "공포 후 N개월(년)이 경과한 날" = 공포일 + N개월의 **다음 날**
  - 검증: 공식 시행예정 버전의 시행일을 정답으로 단위 테스트 (근기법 2026.6.9 공포 → 2026-12-10 · 2027-06-10, 2026.4.7 공포 → 2026-10-08 · 2026-12-08 · 2027-01-01)
- 상태 판정: 기준일(기본값 = 요청일, 요청에 `as_of`로 지정 가능) 대비 `시행 중 · 시행 예정(날짜) · 효력 상실(날짜)`
- 주입 형식: 검색된 청크마다 헤더 부착

```
[근로기준법 제60조 제5항] 상태: 시행 예정 2027-06-10 (부칙 <제21784호,2026.6.9> 제1조)
연결: 시행령 제○조(분할 단위) · 기준일 2026-10-01
<조문 본문>
```

- 연결 확장 범위: 검색 top-k의 1-hop 연결(부칙·위임)만 추가, 토큰 상한 초과 시 위임 조문부터 생략
- 파싱 실패 처리: 부칙 문장 중 규칙으로 해석 못 한 것은 `status=unknown` + 원문 부칙 동봉 → LLM이 원문 근거로 서술, 실패 목록은 인제스트 리포트로 출력
- 한계: 부칙 표현이 정형화되지 않은 타법개정·복잡한 단계 시행은 일부 `unknown` 잔존 → 비율을 README에 기재

### 2.5 응답 거절 로직 (Hallucination 방지 3단)

1. **검색 게이트**: top-1 유사도 < τ → LLM 호출 없이 `insufficient_context` 반환 (τ는 dev split에서 보정)
2. **생성 규칙**: 프롬프트에서 "제공 문맥 외 지식 금지, 근거 없으면 insufficient" 명시, JSON 출력 강제
3. **인용 검증**: 인용 id가 검색 결과 집합에 없거나 인용이 0개 → `insufficient_context`로 강등

### 2.6 Request / Response Schema

```jsonc
// POST /v1/query
{ "question": "string (1~500자)", "top_k": 5, "as_of": "2026-10-01 (선택, 기본값 요청일)", "stream": false }

// 200 OK
{
  "status": "answered | insufficient_context",
  "answer": "string | null",
  "citations": [
    { "chunk_id": "LSA-60-2", "law": "근로기준법", "article": "제60조 제2항",
      "quote": "인용 원문 발췌", "url": "https://www.law.go.kr/...",
      "status": "in_force | pending | expired | unknown", "status_date": "2027-06-10",
      "status_source": "부칙 <제21784호,2026.6.9> 제1조" }
  ],
  "retrieval": [{ "chunk_id": "...", "score": 0.71 }],
  "meta": { "model": "gpt-5.6-luna", "prompt_version": "gen-v1",
            "latency_ms": 1830, "usage": { "input": 2950, "output": 280 }, "cost_krw": 1.4 }
}
```

- Streaming(가산점): `stream=true` 시 SSE — `delta` 이벤트 연속 후 `final` 이벤트에 citations·meta 전송
- 환경 변수: `ELICE_API_KEY`, `ELICE_BASE_URL`, `LLM_MODEL` — `.env.example`만 커밋

## 3. Part B — Eval Harness

### 3.1 Gold Set — 난이도 단계 + 판례 사례형

- 규모: **55문항** (dev 22 / test 33 — 난이도 단계별 층화 분할, τ·프롬프트 조정은 dev만 사용)
- 작성 순서: **L1부터 작성·검증** → 파이프라인이 L1~L2에서 동작 확인된 뒤 L3~L5 확장

| 단계 | 유형 | 문항 | 정답 근거 | 판정 방식 | 예시 |
|---|---|---|---|---|---|
| L1 | 단일 조문 사실 | 10 | 조문 1개 | 조문 문언 대조 | 1주 법정 근로시간 상한 |
| L2 | 수치·조건·단서 | 10 | 조문 1~2개 | 문언 대조 (단서·경계값 주의) | 입사 2개월 차 해고 시 예고 의무 |
| L3 | 다중 조문 · 위임 · 계산 | 10 | 법 + 시행령 | 문언 대조 + 계산 검산 | 근속 5년 차 연차 일수, 상시 근로자 수 산정 |
| L4 | 시점 · 부칙 | 7 | 조문 + 부칙 | 결정적 날짜 대조 | 연차 시간단위 분할 사용 가능 시점 |
| L5a | 판례 사례형 — 법령으로 판단 가능 | 8 | 판결요지 + 적용 조문 | **판결요지 결론과 대조** | 판례 사실관계를 질문으로 재구성 |
| L5b | 판례 사례형 — 해석 의존 | 6 | 판결요지 (법령 본문 밖) | 기대 = `insufficient_context` | 정기상여금의 통상임금 해당 여부 |
| — | Corpus 밖 · 잘못된 전제 | 4 | 없음 | 기대 = `insufficient_context` | 존재하지 않는 제도 전제 질의 |

- **판례 사용 원칙**
  - 판례의 역할 = 현실적 사실관계 공급 + **전문가(법원)가 작성한 정답 근거** → 작성자의 법률 해석 개입 최소화
  - 출처: 대법원 판례 (판결문은 저작권 보호 대상 아님, 저작권법 제7조 제3호) — 사건번호 · 선고일 · 판시사항 · 판결요지를 `eval/gold/cases/`에 저장
  - L5a/L5b 분류 기준: 판결요지의 결론이 **현 Corpus 조문 문언만으로 도출되는가** — 작성자가 조문을 대조해 분류, 근거 메모 필수
  - **시점 필터**: 판결이 적용한 조문이 선고 이후 개정됐으면 제외 또는 "현행 기준" 질문으로 재구성 — 개정 태그로 결정적 확인
  - 정답 = 판결요지 결론, key_points = 판결요지 문장 + 적용 조문 번호
- 항목 스키마

```jsonc
{ "id": "q041", "split": "test", "level": "L5a",
  "question": "...", "expected_status": "answered", "as_of": "2026-10-01",
  "gold_evidence": ["LSA-26"],
  "key_points": ["계속 근로 3개월 미만이면 해고예고 적용 제외"],
  "case": { "id": "대법원 20XX다XXXXX", "decided": "20XX-XX-XX", "holding_ref": "판결요지 1" },
  "classification_note": "판결요지 결론이 제26조 단서 1호 문언으로 직접 도출" }
```

- 구축 방법: L1~L4는 조문 원문 보고 **직접 작성**, L5는 판례 사실관계를 질문으로 재구성, AI 도구는 문장 다듬기에만 사용, 전 항목 원문·판결요지 대조 검증
- 편향·한계 (README 명시 대상)
  - 단일 작성자 → 질의 표현·난이도 분포 편향
  - 작성자가 Chunking 구조를 알고 있음 → 조 단위에 유리한 질의 편중 가능
  - 55문항 → 단계별 건수 지표(6~10건) 통계적 불안정
  - 판례 선정 편향: 쟁점이 명확한 판례 위주 → 실제 분쟁의 모호성 과소 대표
  - L5a/L5b 분류는 작성자 판단 → 경계 사례 존재, 분류 근거 메모로 감사 가능하게 유지

### 3.2 Metric

| # | Metric | 측정 대상 | 방식 | 선정 이유 |
|---|---|---|---|---|
| M1 | Evidence Recall@k · MRR | 검색 | 결정적 (gold_evidence ∩ top-k) | 생성 품질의 상한 결정 요인, 원인 분리 |
| M2 | 거절 정확도 (unanswerable recall · over-refusal rate) | 거절 | 결정적 (status 비교) | Hallucination 방지 요구사항의 직접 측정 |
| M3 | Citation precision | 인용 | 결정적 (인용 ∩ gold_evidence) | 근거 제시 요구사항 직접 측정 |
| **M4** | **Key-point coverage** (정답성) | 생성 | Judge — key_point별 포함 여부 이진 판정 | 요약·추론처럼 정답 문자열이 없는 질의 채점 |
| **M5** | **Unsupported claim rate** (충실성) | 생성 | Judge — 답변을 주장 단위로 분해, 인용 원문 지지 여부 이진 판정 | 그럴듯한 오답(Hallucination) 직접 검출 |
| M6 | 시점 오류율 | 생성 (L4) | Judge 이진 판정 — 미시행·효력 상실 조문을 현행으로 서술했는지 (GT key_point에 시행 상태 명시) | 법령 도메인 고유 Hallucination 유형 |
| — | 비용 · p50/p95 지연 | 운영 | 결정적 | 품질-비용 Trade-off 판단 |

- 주 지표 = **M4 · M5 · M2**, 보조 지표 = M1 · M3 (원인 진단용)

### 3.3 LLM-as-a-Judge 신뢰성 확보

- 위험: 생성 모델 = Judge 모델(Luna 단일) → **자기 선호 편향** 가능
- 완화 설계
  - 1~10점 총평 대신 **체크리스트 이진 판정** — 주관 개입 축소
  - Judge에 인용 원문·key_points 제공 — 모델 사전 지식이 아닌 대조 판정 강제
  - temperature 0, 판정 근거 문장 필수 출력 → 사후 감사 가능
- 검증 절차
  - **Human alignment**: dev 답변 40건 직접 라벨링 → Judge와 일치율·Cohen's κ 측정, 채택 기준 κ ≥ 0.6
  - **일관성**: 동일 입력 3회 판정 → 판정 뒤집힘 비율 측정
  - 기준 미달 시 Judge 프롬프트 수정 후 재측정 (수정 이력 `eval/judge/CHANGELOG.md` 기록)
- 남는 맹점(README 명시): 동일 모델 편향 완전 배제 불가 → 타 계열 Judge 교차 검증은 Next Steps

### 3.4 자동화 파이프라인

- 단일 명령: `make eval CONFIG=configs/baseline.yaml`
- 산출물 `runs/<timestamp>_<config>/`
  - `predictions.jsonl` · `judgments.jsonl` · `report.md` · `report.json`
  - `manifest.json`: git SHA, config 해시, 모델 alias + 응답 model 필드, 임베딩 모델 revision, seed, Corpus 스냅샷 해시, Gold Set 해시, 토큰·비용 합계
- 재현성: LLM 응답 캐시(키 = 프롬프트 해시 + 모델 + 파라미터) → 재실행 시 동일 결과, `--no-cache`로 노이즈 측정
- 비교: `make compare A=<run> B=<run>` → Metric 차이 + 노이즈 바닥 대비 유의 여부 + 문항별 paired bootstrap 95% CI
- **예산 가드**: 실행 전 예상 비용 출력, 실행당 상한 2,000원 초과 시 즉시 중단·보고

### 3.5 노이즈 바닥

- 기준선 config를 `--no-cache`로 **3회** 실행 → Metric별 변동 폭(max−min, 표준편차) 측정
- 판정 규칙: arm 간 차이 < 노이즈 폭이면 "유의하지 않음"으로 보고
- 비율 지표(n=50)는 상대적으로 안정, 유형별 건수 지표(n=5~12)는 불안정 → 보고서에 구분 표기

### 3.6 CI 연동 설계 (가산점, 설계 논의만)

| 트리거 | 실행 범위 | LLM 호출 | 게이트 |
|---|---|---|---|
| 모든 PR | 스키마 테스트 + M1·M3 (검색·인용, 결정적) | 없음 | 기준선 대비 하락 시 실패 |
| `eval` 라벨 PR | dev split 전체 | 캐시 우선 | 노이즈 바닥 초과 하락 시 실패 |
| main 병합 · 야간 | test split 전체 `--no-cache` | 있음 | 결과를 기준선으로 갱신, PR 코멘트 리포트 |

- 비밀값은 CI secret, 실행당 비용 상한 동일 적용
- Gold Set 변경 = 기준선 리셋 이벤트 → 별도 버전(`gold_v2`) 관리

## 4. Part C — 개선 실험

### 4.1 가설 목록

| ID | 변경 | 기대 상승 Metric | 우선순위 |
|---|---|---|---|
| H1 | 고정 512토큰 → **조문 구조 단위 Chunking + 헤더** | M1 Recall@5, M4 coverage | 필수 |
| H2 | Dense 단독 → **BM25(kiwi) + Dense RRF 하이브리드** | M1 (조 번호·용어 일치 질의) | 예산 여유 시 |
| H3 | 거절 임계값 τ 보정 (dev split 곡선 기반) | M2 unanswerable recall, over-refusal과 Trade-off 곡선 | 예산 여유 시 |
| H4 | 시행 상태 연결 주입(2.4) on/off | M4 · M5 (L4 시점 문항), 미시행 조문을 현행처럼 답한 비율 | **필수** |
| H6 | 임베딩 비교: KURE-v1 vs 원본 bge-m3 (한국어 파인튜닝 효과) | M1 Recall@5 · MRR — LLM 호출 없이 검색 지표만으로 비교, 크레딧 0원 | 선택 (필수 실험·README 완료 후) |
| H5 | 판례 판결요지를 Corpus에 추가 | L5b 정답률 (기대 상태가 insufficient → answered로 전환되는 별도 GT 필요) | 선택 |

- H1 공정 비교 조건 (2026-10-01 인덱스 실측): 고정 길이 청크는 평균 3.4개 조문에 걸쳐 "걸치면 적중" 판정이 관대함 → **동일 토큰 예산**(약 2,500토큰)으로 k를 맞춰 비교, 적중은 정답 조문 전문 포함 여부로도 병기
- H4 가설 문장: "최신 공포본 본문만 주입하면 모델은 미시행·효력 상실 조항을 현행처럼 인용한다. 부칙에서 계산한 시행 상태를 조문에 연결해 주입하면 L4 문항의 정답률이 오르고, 미시행 조문을 현행처럼 답한 비율이 내려갈 것이다."
- H1 가설 문장: "고정 길이 분할은 조문을 중간에서 절단하고 출처 경계를 흐린다. 조 단위 분할 + 법령명·조제목 헤더를 적용하면 gold 조문의 검색 순위가 올라 Recall@5와 key-point coverage가 상승할 것이다."
- 각 가설은 노이즈 바닥 측정 후 **2회 반복** 실행
- 결과가 정체·하락해도 원인 분석으로 보고 (과제 명시: 개선 필수 아님)

### 4.2 Report 구조 (README)

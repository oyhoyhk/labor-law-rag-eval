# 노동법령 RAG QA + 자체 Eval Harness

노동 관계 법령 24건과 대법원 판례 400건을 근거로 답하는 Citation 기반 RAG 서비스와, 그 품질을 측정하는 자체 평가 체계

> 설계 문서: [docs/design.md](docs/design.md) · 실측 기록: [docs/findings/](docs/findings/) · 2차 실험 사전 등록: [docs/plans/2026-10-02-part-c-v2-preregistration.md](docs/plans/2026-10-02-part-c-v2-preregistration.md)

## 요약

- **품질 정의**: 답할 수 있는 질문에 필요한 사실을 빠짐없이 말하는가(완전 정답) + 답할 수 없는 질문을 거절하는가 + 근거를 정확히 인용하는가 + 시행 시점을 틀리지 않는가
- **측정**: Gold Set 100문항(전 문항 사람 확인) · 결정적 지표(검색·거절·인용) + 사람 판정으로 보정한 LLM Judge(정답 포인트 κ 0.78) · `make eval` 단일 명령
- **증명 방식**: 동일 설정 3회 반복으로 노이즈 폭 측정 → 노이즈 폭 초과 **그리고** 문항 대응 부트스트랩 95% CI가 0 제외일 때만 개선·악화 판정, 측정 전 가설 사전 등록
- **결과** (GT v2.2)
  - 최종 구성(조 전체 색인 + 판례 연결): 완전 정답 0.692 → **0.772**(CI 하한 0, 경계), 판례형 0 → **0.444(유의)**, 과잉 거절 0.105 → **0.065(유의)**, 인용 정밀도 0.700 → 0.573(유의 악화)
  - 답변까지 유의하게 개선한 단일 변경은 k 5 → 10(완전 정답 +0.069)
  - 평가 체계 개선: 1차(61문항)에서 판정 불가였던 실험 대상 유형(예외·분할)을 GT 확충으로 판정 가능하게 전환, 전체 최소 검출 효과 0.105 → 0.062
- **비용**: 엘리스 크레딧 약 6,000원 사용(5만원 중), 임베딩은 로컬

## Corpus: 노동 관계 법령 24건 + 대법원 판례 400건

- 법령: 근로기준법·최저임금법·근로자퇴직급여 보장법·남녀고용평등법·기간제법·파견법·근로자참여법·임금채권보장법 × (법률·시행령·시행규칙), 조문 894개, 본문 약 255페이지
- 판례: 코퍼스 8개 법률 관련 2010년 이후 대법원 판례 400건(판시사항·판결요지), 참조조문 파싱으로 347건이 조문 150개에 연결
- 출처: 국가법령정보 공동활용 OPEN API(`target=eflaw`, `prec`) 현행본 + 시행예정 버전 11개, 원문 XML 스냅샷을 저장소에 포함(법령·판결은 저작권법 제7조 비보호 저작물)
- 선정 이유
  - 정답이 수치·조건·예외로 결정되어 판정 가능: 조문 문장과 대조해 채점
  - 위임 구조(법 → 시행령 → 시행규칙)와 조문 간 참조로 다중 근거 추론 질의가 자연스럽게 발생
  - **최근 개정으로 모델 사전 지식과 현행 조문이 어긋남** → Hallucination 관측 가능. 문맥 없이 질의(closed-book) 시 오래된 사실 100%, 최근 개정 사실 40% 정답(`docs/findings/2026-10-01-closed-book.md`)
  - 공식 현행본에도 효력을 잃은 조항(근로기준법 제16조, 제53조③⑥)과 시행 전 개정이 섞여 있어, 시점 판단이 필요한 실제 난제 포함
  - 조문만으로 결론이 나지 않고 판례가 결론을 정하는 질문(통상임금, 연차 발생 시점 등)이 실무에서 흔함 → 판례 연결 필요

## 시스템 아키텍처

```
[수집]  law.go.kr OPEN API ──► data/raw/laws/*.xml (현행 + 시행예정) · data/raw/precedents/*.xml (판례 400건)
   │
[인제스트]  make ingest — LLM 호출 없음, 규칙 기반
   ├ parse      법령 XML → 조·항·호 구조 레코드 (app/ingest/parse.py)
   ├ provision  Provision Graph (data/processed/provision_graph.json)
   │             ├ 시행 상태: 시행예정 버전 diff + 부칙 유효기간 → 조문별 시행 중·개정 예정·효력 상실
   │             ├ 위임 연결: 법 ↔ 시행령 ↔ 시행규칙 ("법 제N조" 인용)
   │             ├ 같은 법 안 참조: 예외("에도 불구하고")·준용
   │             └ 조문 → 판례: 판례 참조조문 파싱
   ├ index      KURE-v1 임베딩 → FAISS IndexFlatIP
   │             ├ whole     조 1개 = 벡터 1개 (기본)
   │             ├ article   512토큰 초과 조를 항·호 경계에서 분할 (비교용)
   │             ├ fixed     고정 길이 512토큰 (비교용)
   │             └ precedent 판례 판시사항+판결요지 (연결 판례 정렬용, 검색 대상 아님)
   │
[질의]  POST /v1/query (FastAPI, JSON·SSE)
   ① 조문 검색 top-5
   ② 거절 게이트: 1위 점수 < τ 0.50 → [정보 부족]
   ③ 위임 확장: 검색된 조의 시행령·상위법 최대 3개
   ④ 판례 확장: 검색된 조에 연결된 판례 → 질의 유사도 ≥ 0.54 상위 2건
   ⑤ 블록마다 시행 상태 헤더 주입 ("2026-12-08 시행 예정" 등)
   ⑥ GPT-5.6 Luna 생성 ([S#] 인용, 조문 → 대법원 판단 → 사안별 차이 단서)
   ⑦ 인용 검증 → 응답 (인용마다 조문/판례 구분·시행 상태·원문 링크)
   │
[평가]  make eval
   Gold Set 100문항 ─► 질의 경로 그대로 실행 ─► 결정적 지표(M1~M3) + Luna Judge(M4~M6)
   ─► report.md · scores.jsonl · manifest.json (모델·seed·프롬프트·Corpus·GT 해시·비용)
```

## 실행 방법

### 1. 설치

```bash
uv sync
cp .env.example .env   # LAW_OC, ELICE_API_KEY, ELICE_BASE_URL, LLM_MODEL
```

| 환경 변수 | 용도 |
|---|---|
| `LAW_OC` | 국가법령정보 공동활용 OPEN API 인증키 (수집 시에만, [open.law.go.kr](https://open.law.go.kr) 활용신청) |
| `ELICE_API_KEY` | 엘리스 ML API Serverless 키 |
| `ELICE_BASE_URL` | `https://mlapi.run/v1` |
| `LLM_MODEL` | `openai/gpt-5.6-luna` |

### 2. Corpus 수집 (선택 — 스냅샷이 `data/raw/`에 포함됨)

```bash
uv run python scripts/fetch_laws.py                        # 법령 현행 + 시행예정 버전
uv run python scripts/fetch_precedents.py bulk --max 400   # 코퍼스 법률별 대법원 판례 일괄 수집
```

### 3. 인제스트

```bash
make ingest      # Provision Graph + 인덱스 4종 (whole·article·fixed·precedent), 첫 실행 시 임베딩 모델 내려받기
uv run pytest -q
```

### 4. 서버 실행

```bash
uv run uvicorn app.api:app --port 8000
curl localhost:8000/v1/query -H 'Content-Type: application/json' \
  -d '{"question": "연차휴가를 시간 단위로 쓸 수 있나요?", "as_of": "2026-10-01"}'
# 스트리밍: "stream": true → SSE `delta` 이벤트 후 `final` 이벤트(전체 응답)
```

### 5. 평가 실행

```bash
make eval NAME=final                                          # 기본 구성으로 Gold Set 100문항 → runs/<시각>_final/report.md
make eval NAME=legacy ARGS="--strategy article --no-siblings --no-precedents"   # 2차 실험 기준선 구성
make eval NAME=h4-off ARGS="--strategy article --no-precedents --no-inject"     # 실험 플래그 예
make eval NAME=noise-2 ARGS="--no-cache"                      # 노이즈 측정: 캐시 없이 재실행
make retrieval ARGS="--strategy article"                      # 검색 지표만(LLM 호출 없음)
make compare ARGS="diff eval/results/v2/baseline-v2 runs/<실행> --base-runs eval/results/v2/noise-v2-2 eval/results/v2/noise-v2-3"   # 전체·유형별·dev/test 판정, 기준선은 3회 평균
uv run python -m eval.mde --gold eval/gold/gold_v2.jsonl runs/a runs/b runs/c   # 유형별 최소 검출 효과
make calibrate                                                # Judge vs 사람 판정 일치도(κ)
```

- 실험 플래그: `--strategy whole|article|fixed` · `--k` · `--tau` · `--no-inject` · `--no-links` · `--[no-]siblings` · `--reverse-refs` · `--prompt` · `--[no-]precedents`
- 실행 폴더: `predictions.jsonl`(답변·인용·검색 결과), `judgments.jsonl`(Judge 판정), `scores.jsonl`(문항별 지표), `report.md`, `manifest.json`(git·모델·seed·프롬프트·Corpus·GT 해시·비용)
- 재현성: seed 42·temperature 0 고정, LLM 응답 캐시(`data/cache/llm`, 동일 요청 0원), 실행당 예산 상한(`--budget`)
- 보관 결과: `eval/results/v2/`(2차, GT v2.1), `eval/results/baseline_v1_1`·`exp_*`(1차, GT v1.1)

## 평가 지표와 한계

양성(Positive) 정의: 거절 지표는 "거절", 검색·인용 지표는 "정답 근거 조문", Judge 지표는 "정답 포인트를 말함"

| 지표 | 무엇을 | 방식 | 기준선 → 최종 | 노이즈 폭 | 한계·맹점 |
|---|---|---|---|---|---|
| **M4 완전 정답** (주 지표) | 답할 수 있는 문항에 정답 포인트를 전부 말했나, 거절은 실패 | Judge + status | 0.692(3회 평균) → **0.772** | ±0.033 | 정답 포인트 문구 범위가 작성자 판단 |
| M1 검색 Recall@5 (any·all) · MRR | 정답 조문이 검색됐나 | 결정적 (ID 대조) | 0.924·0.696·0.799 → 0.924·0.696·0.801 | 0 | 판례 근거는 검색이 아닌 연결로만 도달 → L5b의 Recall(all)은 구조적 0 |
| M2 범위 밖 거절 · 과잉 거절 | 답이 없는 질문 거절(TP) · 답할 수 있는데 거절(FP) | status | 1.00·0.105(3회 평균) → 1.00·**0.065** | 0·±0.022 | 범위 밖 8문항으로 표본 작음, 검색 임계값 거절과 모델 거절 미구분 |
| M3 인용 정밀도·재현율 | 정답 근거를 인용했나 | 결정적 | 0.708·0.850 → **0.573**·0.872 | ±0.016·±0.036 | 정답 목록 밖 보조 근거(판례·관련 조)도 오류로 셈 |
| M4 정답 포인트 | 필요한 사실의 비율 | Luna Judge 이진 판정 | 0.888 → 0.910 | ±0.017 | 답변한 문항만으로 계산 → 거절이 늘면 생존자 편향, 그래서 완전 정답을 주 지표로 사용 |
| M5 근거 없는 주장 | 근거 블록에 없는 말 | Luna Judge 주장 분해 | 0.026 → 0.042 | ±0.017 | 사람 기준 κ 0.54, 정밀도 0.375 → 보조 지표 |
| M6 시점 오류 | 시행 전·효력 상실 조문을 현행처럼 말했나 | Luna Judge | 0.071 → 0.000 (14건) | ±0.071 | 표본 14건, 검색 실패 문항은 측정 불가 |

- 기준선 = 2차 실험 기준선(조각 분할 색인·판례 없음), 최종 = 기본 구성(조 전체 색인·판례 연결), 모두 GT v2.2 100문항
- 노이즈 폭: 같은 설정 3회(캐시 없이 2회 재실행)의 max−min (`eval/results/noise_floor.json`)
- 기준선 거절 판단 4칸(1차 61문항): 범위 밖 거절 TP 8 · 환각 FN 0 · 과잉 거절 FP 2 · 정상 답변 TN 49 — 답변한 49건 중 11건은 정답 포인트 일부 누락이라 4칸만으로는 품질을 볼 수 없음 → 완전 정답 지표 도입 근거

## CI 연동 설계 (Regression 방지)

| 단계 | 트리거 | 내용 | LLM 비용 |
|---|---|---|---|
| 빠른 검사 | 모든 PR | `pytest`, `verify_gold`, 검색 지표(`make retrieval`) — 기준선 대비 하락 시 실패 | 0원 |
| 전체 평가 | `eval` 라벨 PR · 야간 | `make eval` 100문항, LLM 응답 캐시로 변경분만 호출, 예산 상한 | 수십~400원 |
| 퇴행 판정 | 전체 평가 후 | `make compare diff 기준선 PR실행` — 전체·유형별 부분집합에서 노이즈 폭과 95% CI를 모두 넘는 하락만 실패 | 0원 |
| 결과 공유 | PR 코멘트 | 지표 표와 악화 문항 목록, `report.md`를 아티팩트로 첨부 | — |

- 비밀값(`ELICE_API_KEY`)은 CI secret, 임베딩 모델은 revision 고정으로 캐시
- Gold Set이 바뀌면(`gold_sha256` 변경) 기준선과 노이즈 폭을 새로 측정하고 이전 기준선과 직접 비교하지 않음
- Judge 프롬프트 변경도 기준선 재고정 사유(`judge_version`)
- 노이즈가 큰 문항(동일 설정 반복에서 결과가 바뀌는 21문항, `noise_floor.json`의 `unstable_items`)은 문항 단위 회귀 알림에서 제외

## Judge 신뢰성

| 지표 | Judge | 사람 확인 판정과 일치 | 채택 |

### 실험에서 드러난 평가 체계의 한계
- **과잉 거절 지표**는 "오답 → 거절" 전환(g013, k=10)도 악화로 셈 → 완전 정답과 함께 보고
- **정답 포인트**는 답변한 문항만으로 계산 → 거절이 늘면 생존자 편향(H1이 높게 보이는 이유) → 거절을 실패로 세는 완전 정답을 주 지표로 채택
- **인용 정밀도**는 GT 정답 근거 목록 밖 인용을 모두 오류로 셈 → 보조 근거와 잘못된 근거 미구분
- **노이즈 문항**: g018·g019·g030·s03 등은 동일 설정 반복에서도 결과가 바뀜 → 개별 문항 변화 해석에서 제외
